## 1. Цель

Отправлять отклонения, выявленные контрольными проверками ReportsTax, в Payroll.Validator: он регистрирует их, создаёт заявку в Process Management и задачу в ДКЗ, затем публикует статусы исправления в Kafka.

Наша зона — шаги 1–4 сквозного процесса (отправка и приём `task_id`) плюс приём статусов из Kafka. Заявка в PM и задача в ДКЗ создаются на стороне Валидатора **после** того, как мы получили ответ.

`NOT_FOUND` — код не найден в Матрице Валидатора, **процесс в PM не запускается, задача не создаётся**.

## 5. Алгоритм отправки

### 5.1. Триггер

Прогон завершён (`DONE`) **и** отклонения есть. Без отклонений не отправляем — `deviations` требует минимум одного элемента.

Создаётся запись `validation_sending_log` со `status = NEW`.

⚠ **Д7. Синхронный вызов.** ТЗ вызывает `sendUnsentResults` прямо в `completeValidationRun` и допускает до 3 повторов с задержками 300/600/1200 мс — то есть завершение прогона может блокироваться на секунды, а на большом объёме упасть по таймауту. Для MVP допустимо при двух условиях: жёсткий таймаут HTTP-клиента и повторы **вне** этого вызова (запись `RETRY_NEEDED` подхватывается отдельным заданием). Целевой вариант — задание, подхватывающее `status IN (NEW, RETRY_NEEDED)`, как для `xml_file.state = SEND_PROCESSING`.

### 5.2. Определение кода

`validation_result.validationCheckCode` → `validation_code_mapping` → `external_code`.

Код не найден или неактивен → отклонение **не отправляется**, прогон помечается как отправленный не полностью, формируется **алерт** (Д8). Формулировка ТЗ «прогон завершается успешно» означала бы тихую потерю отклонения в регуляторной отчётности.

### 5.3. `message`

Формат из ТЗ: `"Отчет: {jobId}, Тип: РНУ НДФЛ, Период: {period}"`.

⚠ **Д9.** Текст не содержит сути отклонения: исполнитель в ДКЗ видит, к какому отчёту оно относится, но не что чинить. В `validation_result` нет ни текста, ни `expected_value` / `actual_value` — они были исключены из модели. Добавить хотя бы наименование проверки из `validation_check_list.name`, а по возможности вернуть в модель ожидаемое и фактическое значения.

### 5.4. `person_id` и `do_id`

`do_id` — из `validation_result.doId`, `null` не передаём.

`person_id`: из `validation_result.personId`; если пусто — резолв через `JobPersonService.findJobPersonsByJobId(jobId)` с фильтром по `do_id`. Не найдено → отправляем без него, WARN. Задача в ДКЗ останется без привязки к сотруднику.

### 5.5. Сборка запроса

```
1. run = findRunById(validationRunId); job = jobRepository.findById(run.jobId)
2. companyId = <Д4>; period = jobPeriodService.getPeriodByJobId(jobId)
3. unsent = findUnsentByRunId(validationRunId)   ← через validation_sending_item
   пусто → return
4. для каждого result:
     externalCode = mapping.getExternalCode(result.validationCheckCode)
     externalCode == null → алерт, пропуск, пометка неполной отправки
     deviation = {
       source_deviation_id: result.getId(),        // Д1: НЕ randomUUID
       validation_business_code: externalCode,
       message: formatMessage(...),
       do_id: result.getDoId(),
       person_id: resolvePersonId(result, jobId)
     }
5. deviations пуст → return
6. request = {
     company_id, source_event_id: run.getId(),
     occurred_at: run.getFinishedAt(),             // Д2: НЕ now()
     event_reason, key_date, data[], deviations[]
   }
7. status = SENDING, attempt_count + 1 → POST
```

## 6. Обработка ответа

### 6.1. HTTP 200

- `status = SENT`, `validator_task_id`, `http_status = 200`, `sent_at`, счётчики `match_found_cnt` / `match_not_found_cnt`, `raw_response`.
- По каждому `events[0].deviations[]` найти `validation_sending_item` по `source_deviation_id` → записать `match_status`.
- **`NOT_FOUND` → алерт.** Отклонение принято, но задача не создана: повторно оно не уйдёт, а до исполнителя не дошло. Пометить прогон как отправленный не полностью.

### 6.2. Ошибки

| Ситуация | Действие |
|---|---|
| 400 | `status = FAILED`, повтор не выполняется |
| **404 `VALIDATION_BUSINESS_CODE_NOT_FOUND`** | `status = FAILED`, повтор не выполняется, **алерт**: код не зарегистрирован у Валидатора, отправка невозможна до регистрации (**Д10** — в алгоритме ТЗ этот код не обработан вовсе) |
| 401 | Обновить токен → одна повторная попытка; не помогло → `RETRY_NEEDED` |
| 500 / таймаут / обрыв | `RETRY_NEEDED`, отложенный повтор, предел 5 попыток, далее инцидент |

⚠ **Зависшая отправка.** Запись не должна остаться в `SENDING` навсегда: правило таймаута переводит её в `RETRY_NEEDED`. Аналогичная дыра выявлена в HRPY-25121 (`DELETE_PROCESSING`).

### 6.3. Идемпотентность — зафиксировано в ТЗ

ТЗ (10.2) прямо признаёт: **идемпотентность не гарантируется**. Каждый запуск `runValidation()` создаёт новый `ValidationRun` с новым UUID ⇒ повторный прогон даёт новый `source_event_id`, и Валидатор обработает его как новое событие. `source_deviation_id` также генерируется заново при каждой отправке.

Это осознанное решение, соответствующее текущему коду. Остаточный риск один: **повторная отправка того же прогона** (после `RETRY_NEEDED` или ручного перезапуска) уйдёт с прежним `source_event_id`, но новыми `source_deviation_id`. Как Валидатор поведёт себя в этом случае — создаст дубли отклонений внутри уже известного события или отбросит — из контракта не следует. Уточнить у Базанова; при неблагоприятном ответе брать `source_deviation_id = validation_result.id`, что даёт стабильность в пределах прогона.

## 7. Отслеживание статусов — вне объёма спринта

**Третий пункт задачи в ТЗ не покрыт.** Синхронный ответ даёт только `task_id` и `match_status`; статусы исправления (`fix_status`: CREATE → COMPLETED / REJECTED) публикуются Валидатором в Kafka `DeviationTaskEvents` — топик виден на sequence-диаграмме контракта, но его описания нет.

Запросить у Базанова: имя топика, схему сообщения, ключ связи (`task_id` и/или `source_deviation_id`), гарантии порядка и повторов.

Заготовка (поля в модели уже есть):
1. Найти `validation_sending_item` по ключу связи; не найдено → игнор с записью в журнал.
2. Событие старше `fix_status_updated_at` → игнор.
3. Иначе записать `fix_status` как пришёл, без локального маппинга (подход `dkz_task`).

## 9. Критерии приёмки

| # | КОГДА | ТОГДА |
|---|---|---|
| 1 | Прогон завершён, отклонения есть, коды определены | Запрос отправлен, `status = SENT`, сохранён `task_id`, на каждое отклонение создана запись `validation_sending_item` |
| 2 | Прогон завершён, отклонений нет | Запрос не отправляется |
| 3 | Код проверки отсутствует в соответствии | Отклонение не отправлено, прогон помечен как отправленный не полностью, **сформирован алерт** |
| 4 | Ответ 200 | По каждому отклонению записан `match_status`, заполнены счётчики |
| 5 | В ответе `match_status = NOT_FOUND` | Статус сохранён, сформирован алерт, отправка считается выполненной |
| 6 | Ответ 404 `VALIDATION_BUSINESS_CODE_NOT_FOUND` | `status = FAILED`, повтор не выполняется, алерт |
| 7 | Ответ 400 | `status = FAILED`, повтор не выполняется |
| 8 | Ответ 401 | Токен обновлён, выполнена повторная попытка |
| 9 | Ответ 500 | `status = RETRY_NEEDED`, `attempt_count + 1`, отложенный повтор |
| 10 | Ответ не получен (таймаут) | Запись не остаётся в `SENDING`, переводится в `RETRY_NEEDED` |
| 11 | Исчерпан лимит попыток | Заводится инцидент, автоматические повторы прекращаются |
| 12 | Повторная отправка **того же** прогона | Прежние `source_event_id` и `source_deviation_id`, дубли задач в ДКЗ не создаются |
| 13 | `person_id` не резолвится | Отклонение отправлено без него, WARN |
| 14 | Прогон на квартальном отчёте крупного департамента | Завершение прогона не блокируется на время сетевого обмена |
| 15 | Получено событие `fix_status` из Kafka | Статус сохранён в `validation_sending_item`; событие старше сохранённого игнорируется |
