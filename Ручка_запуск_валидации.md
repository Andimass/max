# Запуск валидации отчёта РНУ НДФЛ

**Сервис:** Payroll.ReportsTax
**Блок:** Валидация РНУ НДФЛ (схемы `rnu_setting`, `rnu_audit`)
**Основание:** Спецификация на разработку «Блок валидации РНУ НДФЛ (MVP)» — модель данных, алгоритмы проверок, триггер запуска.

---

## Назначение

Валидация запускается автоматически по триггеру перехода отчёта в статус `DONE` (см. п. 3 спецификации). Ручка обеспечивает **ручной запуск валидации** в дополнение к автоматическому.

Сценарии использования:
- **Тестирование проверок.** После изменения данных в БД повторно запустить валидацию и убедиться, что проверка отрабатывает ожидаемо.
- **Контроль.** Запустить валидацию вручную, если автоматический запуск по триггеру не сработал.

Ручка предназначена **только для запуска** прогона. Статус прогона и выявленные отклонения просматриваются по возвращённому `validationRunId` в таблицах `rnu_audit.validation_run` и `rnu_audit.validation_result` через **BI Viewer**.

Алгоритмы проверок, состав реестра и правила фиксации отклонений ручкой не переопределяются — используются согласно спецификации.

---

## Шаг 1. Триггер

Выполняется запрос `POST /v1/rnu/validation`, который в теле содержит следующие параметры:

| Наименование | Тип данных | Описание | Обязательность |
|---|---|---|---|
| `jobId` | string | Идентификатор задачи (запуска отчёта) | Да |

Фильтрация по конкретной проверке или типу проверок в текущей версии не поддерживается — валидация выполняется по всем активным проверкам реестра.

## Шаг 2

Поиск указанного в запросе идентификатора задачи `jobId` в таблице БД `rnu_report.job` в поле `id` при условии, что `status = "DONE"`.

- **а.** Если значение не найдено, см. Альтернативные сценарии п.1. Завершить сценарий.
- **б.** Значение найдено. Переход на след. шаг.

## Шаг 3

В таблице БД `rnu_setting.validation_check_list` отобрать активные проверки при условии `is_active = true`.

- **а.** Если не найдено ни одной активной проверки, см. Альтернативные сценарии п.2. Завершить сценарий.
- **б.** Проверки найдены. Переход на след. шаг.

## Шаг 4

В таблице БД `rnu_audit.validation_run` создать запись со значениями: `job_id` = `jobId` из запроса, `status = "STARTED"`, `started_at` = текущее время. Фиксируем полученный `id`.

Наличие незавершённого прогона (`status = "STARTED"`) по тому же `job_id` не препятствует созданию новой записи: каждый запуск порождает отдельный прогон.

## Шаг 5

**Асинхронно** выполнить прогон валидации согласно п. 3 спецификации «Триггер запуска» (шаги 3–7): построчный обход `rnu_income` в рамках Job через `job_period`, применение активных проверок, фиксация отклонений в `rnu_audit.validation_result` со ссылкой на `validation_run_id` из шага 4, перевод прогона в статус `DONE` (либо `ERROR` при технической ошибке).

## Шаг 6

**Не дожидаясь завершения шага 5**, в ответе возвращаем идентификатор созданного прогона. Завершить сценарий.

| Наименование | Тип данных | Описание |
|---|---|---|
| `validationRunId` | string (uuid) | Идентификатор прогона валидации (`rnu_audit.validation_run.id`) |

**Успешный ответ подтверждает создание и запуск прогона валидации, а не его завершение.** Валидация выполняется асинхронно: при большом объёме данных проверки могут занимать продолжительное время, и синхронный ответ приводил бы к отказу по тайм-ауту.

## Требует подтверждения аналитиком

1. **Путь ручки** — `POST /v1/rnu/validation` предложен по аналогии с `POST /v1/rnu/xml`. Сверить со Swagger проекта ReportsTax.
2. **Условие отбора Job (шаг 2).** В ручке создания XML отбор идёт по `status = "DONE"` **и** `source = "PLANNER"` или `"TAX"`. Для валидации предложено ограничиться `status = "DONE"` — в соответствии с триггером спецификации, где тип отчёта не учитывается. Подтвердить, требуется ли фильтр по `source`.
3. **Повторный запуск (шаг 4).** Предложено разрешать: каждый запуск создаёт отдельный прогон, ранее созданные не изменяются. Ручка предназначена в том числе для перезапуска после изменения данных, поэтому запрет повторного запуска противоречил бы её назначению. Подтвердить.
4. **Разграничение доступа.** Определить круг потребителей ручки: запуск изменяет состояние данных валидации.
5. **Регистрация в API Studio** (проект ReportsTax). На текущем этапе описание ведётся в Confluence; спецификация в API Studio оформляется по получении доступа.

## Дальнейшее развитие (вне текущей версии)

- Необязательные параметры запроса: фильтр по конкретной проверке (`checkCode`) и по типу проверок (`type`).
- Настраиваемый реестр проверок: задание сравниваемых полей и оператора через настройку, без хардкода алгоритма (требует наличия интерфейса настройки).
