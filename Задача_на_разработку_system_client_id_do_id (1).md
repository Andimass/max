# Задача на разработку: `system_client_id` = do_id (string) при отправке НОБ Пульс в МС

**Компонент:** ReportsTax (`app-payroll-reports-tax`)
**Эпик:** Q2.2026_Tax_Общие компоненты · **Security Level:** K-3 · **Команда:** Регуляторная отчётность (PY)
**Связано с:** аналитическая задача system_client_id→do_id (спецификация в разделе «02 Отправка НОБ»), смежная `[HRPY-23866]`.

---

## Описание
При формировании сообщения отправки НОБ Пульс в МС НДФЛ изменить заполнение параметра `system_client_id`: вместо СНИЛС подставлять **do_id**, а тип поля сменить с number на string. Доработка попутно устраняет текущее падение сообщений в DLQ (number не проходит обновлённую валидацию SEDR).

## Что сделать

1. **Источник значения `system_client_id`.**
   В алгоритме формирования сообщения (топик `SRC.MSNDFL.OPERATIONS_PULS.V1`) брать `system_client_id` из `employee_py_nob.do_id` (значение уже есть в отправляемой строке).
   Удалить шаг JOIN с `epk_person_relation.snils`, который сейчас используется только для получения СНИЛС.

2. **Тип поля и JSON-схема — запрос.**
   В схеме сообщения отправки сменить `system_client_id` с `number` на `string` с `maxLength` с запасом (UUID = 36 символов; заложить запас под строгую валидацию SEDR).

3. **Тип поля и JSON-схема — ответ.**
   В схеме ответного сообщения (топик `DST.MSNDFL.OPERATIONS_TO_PULS.V1`) так же привести `system_client_id` к `string` с запасом по длине. Проверить обработку ответа на корректность чтения строкового значения.

4. **Группировка — не трогать.**
   Группировка операций остаётся по `epk_id`; структура `epk_operations` не меняется. Меняется только значение поля.

5. **Валидация.**
   Прогнать обновлённые схемы и примеры сообщений через APIStudio SEDR-валидатор: `https://apistudio-iamosh.sigma.sbrf.ru/#/tools/json` (профиль SEDR). Убедиться, что валидные JSON (запрос и ответ) проходят.

## Порядок / зависимости
- Сначала выполняется эта доработка (поле + схемы), затем — сигнал Бочкареву для синхронной правки на его стороне. **Не менять схему до готовности доработки** — иначе остановится отправка.

## Критерии приёмки
- В сообщении отправки `system_client_id` содержит do_id (значение из `employee_py_nob.do_id`), тип — строка.
- JSON-схемы запроса и ответа обновлены (`system_client_id` = string, maxLength с запасом) и проходят валидацию SEDR.
- Сообщения с do_id в `system_client_id` не уходят в DLQ.
- Группировка по epk_id сохранена, структура `epk_operations` не изменилась.
- Валидные примеры JSON (запрос/ответ) приложены к спецификации.

## Тест-кейсы (минимум)
- Отправка записи из `employee_py_nob` со статусом R → в сообщении `system_client_id` = do_id (string), статус переходит R→P, сообщение проходит SEDR (не DLQ).
- Несколько do_id на одном epk_id → группировка по epk_id сохраняется, в `epk_operations` корректные значения.
- Получение ответа из `DST.MSNDFL.OPERATIONS_TO_PULS.V1` со строковым `system_client_id` → корректная обработка, статус S/E по `status_code`.
