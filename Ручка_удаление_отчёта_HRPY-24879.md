# Удаление отчёта РНУ НДФЛ

**Задача:** HRPY-24879
**Сервис:** Payroll.ReportsTax
**Тип:** REST API

---

## Назначение

Ручка выполняет **полное удаление отчёта** по идентификатору задачи (`jobId`): в рамках **одной транзакции** удаляются записи из всех основных таблиц, относящиеся к данному запуску отчёта.

**Удаление выполняется строго по одному `job` (запуск по департаменту).** Запись `job_company` (запуск по всей компании) не удаляется: на неё могут ссылаться другие `job` по иным департаментам. Массовое удаление всех `job` в рамках одного `job_company` в текущей версии не поддерживается — для этого выполняется отдельный вызов ручки по каждому `jobId`.

Удаление возможно не всегда — см. ограничения (шаги 3 и 4).

---

## Шаг 1. Триггер

Выполняется запрос `DELETE /v1/rnu/report`, который в теле содержит следующие параметры:

| Наименование | Тип данных | Описание | Обязательность |
|---|---|---|---|
| `jobId` | string (uuid) | Идентификатор задачи (запуска отчёта) | Да |

## Шаг 2

Поиск указанного в запросе идентификатора задачи `jobId` в таблице БД `rnu_report.job` в поле `id`.

- **а.** Если значение не найдено, см. Альтернативные сценарии п.1. Завершить сценарий.
- **б.** Значение найдено. Фиксируем `status`. Переход на след. шаг.

## Шаг 3. Проверка ограничения 1 — отчёт отправлен в ФП НДФЛ

В таблице БД `rnu_report.job_period` осуществить поиск `id`, где `job_id` = `jobId` из запроса. По найденным `job_period_id` отобрать записи в таблице `rnu_report.xml_file`.

Проверить значение поля `state`:

- **а.** Если хотя бы одна запись имеет `state = "SEND_SUCCESS"` или `state = "SEND_PROCESSING"`, удаление запрещено. См. Альтернативные сценарии п.2. Завершить сценарий.
- **б.** Иначе (все записи в статусе `CREATED` / `SEND_ERROR`, либо записи отсутствуют). Переход на след. шаг.

> Отчёт, успешно отправленный в ФП НДФЛ либо находящийся в процессе отправки, удалению не подлежит. Статусы `CREATED` (файл создан) и `SEND_ERROR` (ошибка отправки) удалению не препятствуют.

## Шаг 4. Проверка ограничения 2 — отчёт в процессе формирования

Проверить значение `status` записи `rnu_report.job`, зафиксированное на шаге 2.

- **а.** Если `status = "PROCESSING"` (отчёт в процессе формирования), удаление запрещено. См. Альтернативные сценарии п.3. Завершить сценарий.
- **б.** Иначе (`CREATED` / `DONE` / `ERROR`). Переход на след. шаг.

> Удаление данных не прерывает формирование отчёта: механизм отмены Job в системе не предусмотрен (перечень статусов — `CREATED`, `PROCESSING`, `DONE`, `ERROR`). При удалении отчёта в статусе `PROCESSING` процесс формирования продолжит запись данных по удалённой задаче, что приведёт к нарушению целостности. Поддержка удаления отчётов в процессе формирования требует реализации отмены Job и в объём задачи не входит.

## Шаг 5. Удаление

В рамках **одной транзакции** удалить записи, относящиеся к `jobId`, из основных таблиц. Порядок удаления — от дочерних таблиц к родительским, с учётом внешних ключей:

| № | Таблица | Условие отбора |
|---|---|---|
| 1 | `rnu_xml_sending_log` | по `xml_file_id` удаляемых записей `xml_file` |
| 2 | `person_id_xml` | по `job_period_id` |
| 3 | `xml_file` | по `job_period_id` |
| 4 | `external_xml_file` | по `job_period_id` |
| 5 | `external_rnu` | по `job_id` |
| 6 | `rnu_deduction` | по `job_period_id` (в таблице есть также `income_id`) |
| 7 | `rnu_advance_payment` | по `job_period_id` (в таблице есть также `income_id`) |
| 8 | `rnu_income` | по `job_period_id` |
| 9 | `rnu_person_data` | по **`job_id`** |
| 10 | `py_dm_integration` | по `job_id` |
| 11 | `job_person` | по `job_id` |
| 12 | `job_period` | по `job_id` |
| 13 | `job` | по `id` = `jobId` |

Запись `job_company` **не удаляется** (см. «Назначение»).

**Внешние XML включены в удаление.** Таблица `external_rnu` (входящий РНУ из ЕАСУП/САП) содержит FK `job_id`, `external_xml_file` — `external_rnu_id` и `job_period_id`, а `person_id_xml` содержит `external_xml_file_id` наряду с `xml_file_id`. Входящие данные привязаны к тому же Job, поэтому удаляются вместе с отчётом — иначе останутся записи со ссылкой на несуществующую задачу.

При возникновении ошибки на любом шаге — **транзакция откатывается целиком**, данные отчёта остаются в исходном состоянии.

## Шаг 6

По завершении шага 5 возвращаем успешный ответ. Завершить сценарий.

| Код HTTP | Описание |
|---|---|
| 200 | Отчёт удалён |

---

## Альтернативные сценарии (АС)

| Пункт АС | Код HTTP | Номер сообщения | Текст сообщения |
|---|---|---|---|
| 1 | 404 | 1 | Идентификатор задачи не найден |
| 2 | 409 | 2 | Отчёт отправлен в ФП НДФЛ, удаление невозможно |
| 3 | 409 | 3 | Отчёт находится в процессе формирования, удаление невозможно |

## Открытые вопросы

**1. Внешние XML — подтвердить включение в удаление.**
`external_rnu` и `external_xml_file` включены в перечень удаляемых таблиц на основании их привязки к Job (FK `job_id` / `job_period_id`). Требуется подтверждение аналитика: удаляются ли входящие РНУ из ЕАСУП вместе с отчётом Пульса, либо сохраняются как данные внешней системы (в этом случае потребуется решение по осиротевшим ссылкам).

**2. Расхождение ER-модели и Confluence.**
В актуальной ER-модели (v.1) отсутствуют таблица `job_company` и поле `job.job_company_id`, при этом на странице структуры данных (п. 1.1) они описаны. ER-модель отстаёт от требований — при разработке ориентироваться на Confluence.

**3. Тип удаления.** Предложено физическое удаление записей. Подтвердить, не требуется ли логическое удаление (пометка) для целей аудита.

**4. Путь ручки** — `DELETE /v1/rnu/report` предложен по аналогии с `POST /v1/rnu/xml`. Сверить со Swagger проекта ReportsTax.

**5. Разграничение доступа.** Ручка выполняет необратимое удаление данных отчёта — определить круг потребителей.
