# Change: Добавить проверку «вычет > доход» в механизм валидации РНУ НДФЛ

> **Статус**: На согласовании
> **Дата**: 2026-07-30
> **Целевая спецификация**: `openspec/specs/app-payroll-reports-tax/app-payroll-reports-tax.md`
> **Связанные**: проверки 2001 (исчисл. налог), 2002 (НОБ > доход) — реализованы

---

## 🔴 Блокеры — требуют решения до старта разработки

**Б1. Построчно или агрегатом?**
В маппинге проверок зафиксировано: *вычет = `SUM(rnu_deduction.amount)` по `income_id`*, и отдельно — «проверки с вычетами построчные (агрегат дочерних строк одной строки дохода)». Это **агрегатное** сравнение, а не построчное.

Разница существенна: доход 100 ₽ и три вычета по 60 ₽ — при построчном сравнении проверка промолчит, при агрегатном сработает. Второй случай и есть реальная ошибка данных.

Ниже основным описан **агрегатный** вариант как соответствующий спеке. Построчный вариант — в приложении А. Подтвердить у М.Г. Пахомовой.

**Б2. Код проверки.**
В официальном реестре проверок у строки «вычет > доход» **код отсутствует** (прочерк; коды есть только у 2001 и 2002). `2003` — наше предложение по аналогии. Подтвердить у постановщика, чтобы не разойтись с реестром.

**Б3. Проверка вне MVP.**
В реестре строка «вычет > доход» помечена как **не входящая в MVP** — в MVP взяты 2001 и 2002 именно потому, что они «чистые», без хождения в `rnu_deduction`. Убедиться, что решение о расширении объёма принято.

---

## 1. Что сделать

Добавить в `RnuValidationServiceImpl` логическую проверку: если сумма вычетов по строке дохода превышает сам доход — записать отклонение в `rnu_audit.validation_result`.

---

## 2. SQL-миграция

```sql
INSERT INTO rnu_setting.validation_check_list (code, name, type, block, description, is_active)
VALUES ('2003', 'вычет > доход', 'LOGICAL', 'DEDUCTION',
        'Сумма налоговых вычетов по строке дохода превышает сумму дохода',
        true)
ON CONFLICT (code) DO UPDATE
SET name = EXCLUDED.name, type = EXCLUDED.type, block = EXCLUDED.block,
    description = EXCLUDED.description, is_active = EXCLUDED.is_active;
```

`is_active = true` — проверка включается сразу после раската. (В исходных материалах здесь было противоречие: в одном разделе `false`, в другом `true`. Фиксируем `true`; если нужен раздельный ввод — менять и значение, и критерии приёмки 6–7 согласованно.)

## 3. Изменения кода

### 3.1. Новый метод проверки

```
check2003(BigDecimal deductionsSum, RnuIncome income):
  - deductionsSum IS NULL          → return false
  - income.incomeAmount IS NULL    → return false
  - return deductionsSum.compareTo(income.incomeAmount) > 0
```

Сравнение точное, без допуска: оба поля `numeric(15,2)`, округление здесь не применяется (в отличие от 2001, где `tax_calculated` считается в полных рублях).

### 3.2. Расширить `executeValidationRun`

Проверка 2003 **не встраивается в общий `switch`** с 2001/2002. У income-проверок единица проверки — строка `rnu_income` по её же полям; у 2003 нужны дочерние строки `rnu_deduction`. Сигнатуру `isDeviation()` не трогаем, чтобы не задеть сданные 2001/2002 — добавляем отдельную ветку.

```
for jobPeriodId in jobPeriods(jobId):
    incomes = rnuIncomeRepository.findByJobPeriodId(jobPeriodId)
    if incomes.isEmpty(): continue

    // существующий цикл — без изменений
    for income in incomes:
        for check in activeChecks:
            if check.code == "2001": if check2001(income) → saveResult(check, income)
            if check.code == "2002": if check2002(income) → saveResult(check, income)

    // новая ветка
    check2003 = activeChecks.find(code == "2003")
    if check2003 != null:
        incomeIds = incomes.map(RnuIncome::getId)
        deductions = rnuDeductionRepository.findByJobPeriodIdAndIncomeIds(jobPeriodId, incomeIds)
        if deductions.isEmpty(): continue

        // агрегат по income_id
        sumByIncomeId = deductions.stream()
            .filter(d -> d.amount != null)
            .collect(groupingBy(RnuDeduction::getIncomeId, reducing(ZERO, RnuDeduction::getAmount, BigDecimal::add)))

        incomeById = incomes.stream().collect(toMap(RnuIncome::getId, identity))

        for (incomeId, deductionsSum) in sumByIncomeId:
            income = incomeById.get(incomeId)
            if income == null: continue          // осиротевший вычет — не наша проверка
            if check2003(deductionsSum, income):
                saveResult(check2003, income, incomeId)
```

Загрузка вычетов — **одним запросом на `job_period_id`**, без обращения к БД внутри цикла (N+1).

## 4. Запись отклонения

Поля `rnu_audit.validation_result` — строго по действующей модели:

| Поле | Значение | Комментарий |
|---|---|---|
| `id` | uuid | генерируется |
| `validation_run_id` | id текущего прогона | FK |
| `validation_check_list_id` | `'2003'` | ⚠ **varchar(25)**, FK на `validation_check_list.code` — PK реестра именно `code`, не суррогатный uuid |
| `table` | **`rnu_income`** | ⚠ enum значения: `rnu_income / rnu_person_data / rnu_deduction / rnu_advance_payment`. `DEDUCTION` — значение из **другого** enum'а (`validation_check_list.block`), сюда не подходит |
| `table_entry_id` | `income.id` | при агрегатном варианте единица отклонения — строка дохода |
| `do_id` | `income.doId` | берётся напрямую из `rnu_income` |
| `person_id` | см. ниже | в `rnu_income` поля `person_id` **нет** |
| `created_at` | now() | |

**Резолв `person_id`:** `rnu_income.taxpayer_id` → `rnu_person_data` по паре (`job_id`, `taxpayer_id`) → `person_id`. Альтернатива — через `job_person` по `do_id`. Выбрать один способ и зафиксировать; формулировка «если доступен» из исходника нерабочая — нужно однозначное правило либо явное разрешение писать NULL.

**Записываем только отклонения.** Пройденные проверки в `validation_result` не попадают.

---

## 5. Завершение прогона

Без изменений механики: по окончании обхода `validation_run.status = DONE`, `finished_at = now()`, `deviations_count` = суммарное число записей `validation_result` по всем активным проверкам прогона (2001 + 2002 + 2003).

---

## 6. Что должно получиться

| Вход | Ожидаемый результат |
|---|---|
| `SUM(deduction.amount) > income.income_amount` | одна запись `validation_result`, `table = rnu_income`, `table_entry_id = income.id` |
| `SUM(deduction.amount) <= income.income_amount` | ничего |
| у всех вычетов строки `amount IS NULL` | ничего |
| часть вычетов с `amount IS NULL` | NULL-строки исключаются из суммы, остальные суммируются |
| `income_amount IS NULL` | ничего |
| `deduction.income_id` не ссылается на существующий доход | ничего (обрабатывается отдельной проверкой) |
| несколько вычетов на один доход, сумма > дохода | **одна** запись на строку дохода (не по одной на каждый вычет) |
| вычетов по строке дохода нет | ничего |

## 7. Критерии приёмки

| # | КОГДА | ТОГДА |
|---|---|---|
| 1 | Job РНУ НДФЛ сформирован, по строке `rnu_income` сумма вычетов превышает `income_amount` | Создана запись `validation_result` с `validation_check_list_id = '2003'`, `table = rnu_income`, `table_entry_id = income.id`, заполнены `do_id` и `person_id` |
| 2 | Все вычеты ≤ дохода либо вычетов нет | Записей с кодом `2003` нет |
| 3 | У всех вычетов строки `amount IS NULL` | Записей с кодом `2003` нет |
| 4 | `rnu_deduction.income_id` указывает на несуществующий доход | Записей с кодом `2003` нет, прогон завершается со статусом DONE (не ERROR) |
| 5 | На одну строку дохода приходятся 3 вычета, их сумма > дохода | Создана **ровно одна** запись `validation_result` |
| 6 | `validation_check_list.is_active = false` для кода `2003`, данные с превышением есть | Записей с кодом `2003` нет |
| 7 | `is_active` переведён в `true`, запущена валидация по существующему Job через `POST /v1/rnu/validation` | Отклонения появляются без пересоздания Job |
| 8 | Полный прогон на наборе с отклонениями по 2001, 2002 и 2003 | `validation_run.status = DONE`, `deviations_count` = сумма отклонений по трём кодам |
| 9 | Прогон на объёме одного квартала по крупному департаменту | Число SQL-запросов к `rnu_deduction` не превышает числа `job_period` (отсутствие N+1) |

Критерий про «статус отклонения ERROR» из исходной версии **удалён**: в `validation_result` нет поля под статус или критичность. Тип проверки хранится в `validation_check_list.type = LOGICAL` и оттуда же трактуется потребителем.

## 8. Границы изменения

**Не затрагивается:** контракт `POST /v1/rnu/validation` (в ответе по-прежнему только `validationRunId`, запуск асинхронный); структура `validation_run` и `validation_result`; проверки 2001 и 2002; интеграции, Kafka-топики, конфигурация, авторизация.

**Триггер** прежний: переход `job.status → DONE`, `report_type` не учитывается.

⚠ Путь ручки — `POST /v1/rnu/validation`. В одном из исходных вариантов фигурировал `/api/v1/rnu/validation`; сверить со Swagger ReportsTax перед сдачей.

## 10. Зависимости от открытых замечаний к модели

Проверка 2003 упирается в те же незакрытые пункты, что и MVP:

- **`table` — зарезервированное слово SQL**, колонку с таким именем не создать. Ожидается переименование в `source_table` / `table_name`; в этой постановке имя указано как в исходной модели — при переименовании поправить.
- **FK `validation_check_list_id`** должен быть `varchar(25)` на `validation_check_list.code`. В исходной модели FK указывал на несуществующую таблицу `validation_check`.
- **`is_active` без `NOT NULL DEFAULT true`**: при NULL условие `is_active = true` не выполнится и проверка молча выпадет из прогона.
- **Схема `rnu_audit` должна быть подключена к BI Viewer** — иначе результаты негде смотреть.

## Приложение А. Построчный вариант (если Б1 решится в его пользу)

Если подтвердится сравнение каждой строки вычета с доходом по отдельности:

- агрегация `sumByIncomeId` убирается, цикл идёт по `deductions`;
- `check2003(deduction.amount, income)`;
- `table = rnu_deduction`, `table_entry_id = deduction.id`;
- критерий 5 меняется на «создана отдельная запись на каждый вычет»;
- строка таблицы 6 «несколько вычетов на один доход» — соответственно.

Остальное (резолв `person_id`, отсутствие поля статуса, границы изменения) — без изменений.
