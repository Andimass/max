# Payroll.ReportsTax → Payroll.Validator. Передача отклонений РНУ НДФЛ

**Сервис:** Payroll.ReportsTax · **Статус:** черновик (на согласование)

## 1. Назначение
API для передачи массива отклонений по проверкам РНУ НДФЛ из Payroll.ReportsTax в Payroll.Validator.

`POST /api/v1/deviations/reportstax` · Base Path: `/api/v1` · Content-Type: `application/json` · Accept: `application/json`

## 2. Запрос
### 2.1. Тело
| Атрибут | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| messageId | string (UUID) | Да | Идентификатор запроса (идемпотентность) | 9f3c2a1e-7d6b-4f0a-9c3a-1b2c3d4e5f60 |
| items | array | Да | Массив отклонений (minItems = 1) | [ { … } ] |

### 2.2. items[]
| Атрибут | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| codeId | string | Да | Внешний код проверки (← validation_check.code) | V_004 |
| doId | string (UUID) | Да | ID договорных отношений | 74c0ffd1-5bb7-4b75-bff3-75f7d34c3365 |
| personId | string (UUID) | Да | Идентификатор сотрудника | 434e33ab-0dad-4a52-85c9-5e2ac727684e |
| message | string (≤1000) | Нет | Текст отклонения | База НДФЛ не равна доходу за вычетом |
| verificationStatus | string (enum) | Да | Результат проверки | DEVIATIONS_FOUND |
| businessService | string (enum) | Да | Бизнес-сервис | Payroll.ReportsTax |
| verificationDate | string (YYYY-MM-DD) | Да | Дата выявления | 2026-10-13 |
| verificationTime | string (HH:MM:SS) | Да | Время выявления | 13:00:45 |

`additionalProperties: false`. ФИО/компанию не передаём — Валидатор берёт из своей витрины.

## 3. Ответ
`202 Accepted`
```json
{ "messageId": "9f3c2a1e-7d6b-4f0a-9c3a-1b2c3d4e5f60",
  "taskId":    "bde9a0ad-f672-4f2e-b89e-fb3b70b8da9a" }
```
`taskId` — номер заявки на исправление в журнале Payroll.Validator.

## 4. Ошибки
**400 Bad Request** — `JSON_PARSE_ERROR` (нарушен синтаксис JSON).
**422 Unprocessable Entity** — тело валидный JSON, но данные некорректны. `details[]` с полями `code`, `field`, `index`, `message`:

| code | Условие |
|---|---|
| REQUIRED_FIELD_MISSING | Отсутствует обязательное поле |
| INVALID_FORMAT | UUID / дата (YYYY-MM-DD) / время (HH:MM:SS) не того формата |
| MAPPING_NOT_FOUND | codeId не зарегистрирован в Матрице для businessService=Payroll.ReportsTax |
| INVALID_VALUE | Значение enum (verificationStatus, businessService) вне перечня |

## Приложение А. Процесс (кратко)
1. Событие `dmheaders` (топик `hrp.app.payrolldatamarket.domain.dmheaders`) → создаём прогон `validation_run`.
2. Запрос данных у DataMarket (`POST /v1/dataset`).
3. Предусловие «данные получены»; при пустоте/превышении порога → системный сбой (Приложение В).
4. Предметные проверки → `validation_result`; свёртка по ФЛ → `validation_summary`.
5. Вердикт ОК/не ОК → УОД (гейт платёжек); отклонения → Валидатор (раздел 1–4) → `task_id`.
6. По закрытию заявки — переформирование РНУ по ФЛ и перепроверка.

## Приложение Б. Модель данных
| Таблица | Назначение |
|---|---|
| rnu_setting.validation_check | Реестр проверок (тип, важность, правило, применимость, маршрутизация, предусловие) |
| rnu_setting.validation_check_action | Рекомендации по получателю (нормализовано) |
| rnu_report.validation_run | Прогон: счётчики, флаги системного сбоя/подавления рассылки |
| rnu_report.validation_result | Лог результатов (проверка × запись); источник отправки |
| rnu_report.validation_summary | Вердикт по сотруднику; гейт XML и платёжек |
| rnu_report.validation_sending_log | Аудит исходящих (Валидатор/УОД) |

Детальная спецификация полей — DDL `validation_block_db_full.sql`.

## Приложение В. Краевые случаи (анти-лавина)
- **Пустой расчёт** → предусловие фиксирует системный сбой (`systemic_failure`), рассылка по ФЛ подавляется (`send_suppressed`), наружу один технический сигнал в техподдержку (`cause=TECHNICAL`), в УОД «не ОК на прогон» по тех. причине.
- **Массовые ошибки** → батчинг в один запрос (`items[]`); при превышении порога — режим системного сбоя. Порог — в `constant_set`.

## Приложение Г. Вывод в УОД (на согласование)
Вердикт ОК/не ОК как гейт платёжек. На согласование с УОД: канал (Kafka/REST), формат, грейн (ФЛ/прогон), признак тех. причины. Предлагаемый состав: `job_id`, `job_period_id`, `person_id`/`do_id`, `validation_status`, `error_count`, `cause`.

## Приложение Д. Открытые вопросы
1. Имя endpoint `/deviations/reportstax`, значение `businessService=Payroll.ReportsTax`, регистрация `codeId` в Матрице.
2. Несёт ли item локализацию налоговой ошибки (operation/income/период) или работаем по ФЛ + дриллбэк.
3. Контракт вывода в УОД.
4. Механика петли исправления (возврат «исправлено»).
5. Подписка: `dmheaders` (ЗОД) и/или `secondsign` (финальные данные).
6. Грейн `validation_summary`; каталог проверок и `error_code`; не дублируем ли Матрицу (`responsible_role`/`send_to_dkz`).
