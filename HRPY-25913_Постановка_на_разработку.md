# Change: Добавить проверку 2004 «баланс» (база <> доход - вычет)

> **Статус**: На согласовании
> **Дата**: 2026-07-30
> **Целевая спецификация**: `openspec/specs/app-payroll-reports-tax/app-payroll-reports-tax.md`

---

## Что сделать

Добавить в `RnuValidationServiceImpl` алгоритмическую проверку: сумма дохода должна равняться сумме базы + сумме вычетов. Если формула не сходится — записать отклонение.

Формула: `baseAmount == ROUND(incomeAmount - SUM(deduction.amount), 2)`

---

## 1. SQL-миграция

```sql
INSERT INTO rnu_setting.validation_check_list (code, name, type, block, description, is_active)
VALUES ('2004', 'база <> доход - вычет', 'ALGORITHMIC', 'INCOME',
        'Сумма дохода не равна сумме базы за вычетом суммы налоговых вычетов',
        true)
ON CONFLICT (code) DO UPDATE
SET name = EXCLUDED.name, type = EXCLUDED.type, block = EXCLUDED.block,
    description = EXCLUDED.description, is_active = EXCLUDED.is_active;
```

## 2. Изменения кода

### 2.1. Новый метод проверки

```
check2004(BigDecimal deductionsSum, RnuIncome income):
  - income.incomeAmount IS NULL → return false
  - income.baseAmount IS NULL   → return false
  - deductionsSum IS NULL       → deductionsSum = 0
  - expectedBase = ROUND(incomeAmount - deductionsSum, 2)
  - return expectedBase.compareTo(baseAmount) != 0
```

Сравнение после округления до 2 знаков (числа `numeric(15,2)`, плавающая погрешность при вычитании).

### 2.2. Расширить executeValidationRun — вынести агрегацию вычетов в общий блок

Проверка 2003 и 2004 **использует одни и те же данные** — агрегацию `SUM(deduction.amount)` по `income_id`. Текущая реализация `executeValidationRun()` обходит incomes в цикле и вызывает `isDeviation()` по каждой проверке из `activeChecks`. Для 2001/2002 это работает (проверки смотрят только на поля самой строки `rnu_income`), но для 2003 и 2004 нужен доступ к дочерним строкам `rnu_deduction`.

**Действие:** добавить отдельную ветку после существующего цикла 2001/2002 — один SQL-запрос на `job_period`, группировка `sumByIncomeId`, обработка incomes с вычетами (для 2003 и 2004) и без вычетов (только для 2004).

```
for jobPeriodId in jobPeriods(jobId):
    incomes = rnuIncomeRepository.findByJobPeriodId(jobPeriodId)
    if incomes.isEmpty(): continue

    // --- существующий цикл 2001/2002 — без изменений ---
    for income in incomes:
        for check in activeChecks:
            if check.code == "2001": if check2001(income) → saveResult(check, income)
            if check.code == "2002": if check2002(income) → saveResult(check, income)

    // --- новая ветка: агрегация вычетов для 2003 и 2004 ---
    check2003 = activeChecks.find(code == "2003")
    check2004 = activeChecks.find(code == "2004")

    if check2003 != null or check2004 != null:
        incomeIds = incomes.map(RnuIncome::getId)
        // rnuDeductionRepository — новый метод (см. раздел 2.3)
        deductions = rnuDeductionRepository.findByJobPeriodIdAndIncomeIds(jobPeriodId, incomeIds)

        // агрегат по income_id — один SQL-запрос, без N+1
        sumByIncomeId = deductions.stream()
            .filter(d -> d.amount != null)
            .collect(groupingBy(RnuDeduction::getIncomeId,
                               reducing(ZERO, RnuDeduction::getAmount, BigDecimal::add)))

        incomeById = incomes.stream().collect(toMap(RnuIncome::getId, identity))

        // 1) обрабатываем incomes с вычетами — для 2003 и 2004
        for (incomeId, deductionsSum) in sumByIncomeId:
            income = incomeById.get(incomeId)
            if income == null: continue

            if check2003 != null:
                if check2003(deductionsSum, income):
                    saveResult(check2003, income)

            if check2004 != null:
                if check2004(deductionsSum, income):
                    saveResult(check2004, income)

        // 2) обрабатываем incomes БЕЗ вычетов — только 2004 с deductionsSum = 0
        if check2004 != null:
            for income in incomes:
                if incomeById.containsKey(income.id): continue  // уже проверили выше
                if check2004(0, income):
                    saveResult(check2004, income)
```

List<RnuDeduction> findByJobPeriodIdAndIncomeIds(UUID jobPeriodId, List<UUID> incomeIds);

### 2.4. Расширить isDeviation() (заглушка)

Текущий `isDeviation()` обрабатывает только `2001` и `2002`. После добавления 2004 switch расширится:

```java
case "2003" -> check2003(income);  // уже добавлено (см. change для 2003)
case "2004" -> check2004(income);
```

> **Важно:** Метод `check2004(RnuIncome)` с одним параметром — это **заглушка для switch/case**, которая принимает income и извлекает `incomeAmount` и `baseAmount`. Фактическая проверка происходит в ветке `executeValidationRun` с уже посчитанной `deductionsSum`. Альтернативный вариант: **не добавлять case в isDeviation()**, а вынести проверку 2004 в отдельную ветку, как для 2003.

## 3. Запись отклонения

Поля `rnu_audit.validation_result` — строго по действующей модели сущности `ValidationResult`:

| Поле | Значение | Комментарий |
|------|----------|-------------|
| `id` | `UUID.randomUUID()` | генерируется |
| `validation_run_id` | id текущего прогона | FK |
| `validation_check_code` | `'2004'` | varchar(25), FK на `validation_check_list.code` |
| `table` | `rnu_income` | enum: `rnu_income` / `rnu_person_data` / `rnu_deduction` / `rnu_advance_payment` |
| `table_entry_id` | `income.id` | единица отклонения — строка дохода (не вычет) |
| `do_id` | `income.doId` | берётся напрямую из `rnu_income` |
| `person_id` | см. ниже | в `rnu_income` поля person_id нет |
| `created_at` | `LocalDateTime.now()` | — |

**Резолв person_id**: `rnu_income.taxpayer_id` → `rnu_person_data` по паре `(job_id, taxpayer_id)` → `person_id`. Альтернатива (уже реализована в коде): через `job_person` по `do_id`. Используется второй вариант: `JobPersonService.findJobPersonsByJobId(jobId) → Map<doId, personId>`.

## 4. Интеграция с отправкой в Валидатор

Отклонения по 2004 **попадают в отправку** к `POST /api/v1/deviations` наряду с 2001, 2002, 2003.

### 4.1. Маппинг в validation_matrix

В change HRPY-25913 (раздел 1.1) добавить маппинг:

```sql
INSERT INTO rnu_setting.validation_matrix (internal_code, external_code)
VALUES ('2004', 'V_004')
ON CONFLICT (internal_code) DO UPDATE SET
    external_code = EXCLUDED.external_code,
    is_active = EXCLUDED.is_active,
    updated_at = now();
```

> **Важно:** Без записи в `validation_matrix` отклонение по 2004 **не будет отправлено** (см. HRPY-25913, раздел 2.1: «если external_code не найден — не отправлять»).

### 4.2. Процесс отправки

Отклонение по 2004 собирается вместе с другими отклонениями:
1. `ValidatorDeviationSenderService.sendUnsentResults(validationRunId)` ищет все `validation_result` для прогона.
2. Для каждого `validation_check_code = '2004'` делается запрос в `validation_matrix` → `external_code = 'V_004'`.
3. Формируется батч `ValidatorDeviationRequest` и отправляется в Валидатор.
4. Результат записывается в `validation_sending_log`.

## 5. Завершение прогона

Без изменений: `validation_run.status = DONE`, `finished_at = now()`, `deviations_count` = сумма отклонений по всем активным проверкам прогона (2001 + 2002 + 2003 + 2004).

Записываем только отклонения. Пройденные проверки в `validation_result` не попадают.

## 6. Что должно получиться

| Вход | Ожидаемый результат |
|------|---------------------|
| `baseAmount == ROUND(incomeAmount - SUM(deduction.amount), 2)` | ничего |
| `baseAmount != ROUND(incomeAmount - SUM(deduction.amount), 2)` | одна запись `validation_result` с `validation_check_code = '2004'` |
| `incomeAmount IS NULL` | ничего |
| `baseAmount IS NULL` | ничего |
| вычетов нет (`SUM = 0`), `baseAmount == incomeAmount` | ничего |
| вычетов нет, `baseAmount != incomeAmount` | одна запись `validation_result` |
| вычетов нет, `baseAmount IS NULL` или `incomeAmount IS NULL` | ничего |
| `deduction.income_id` не ссылается на существующий доход | ничего |
| маппинг в `validation_matrix` для 2004 настроен | отклонение отправлено в Валидатор |
| маппинга в `validation_matrix` для 2004 нет | отклонение не отправлено, error логируется |
