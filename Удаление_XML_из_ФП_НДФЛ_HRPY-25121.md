# Удаление XML-файла (ПНФ) из ФП НДФЛ

**Задача:** HRPY-25121 [SA] Удаление xml файла из ФП НДФЛ
**Сервис:** Payroll.ReportsTax · **Эпик:** Q3.2026_Tax_РНУ НДФЛ · **КЭ:** ReportsTax(8449473) · K-3
**Основание:** спецификация ФП НДФЛ «Метод удаления ПНФ» (pageId 21213303047); «Справочник ошибок, возвращаемых в рамках интеграции с системами-источниками» (pageId 23244344511); образец — «5. Отправка XML файла в ФП НДФЛ» (pageId 22422324714).

---

## Назначение

Ранее отправленный в ФП НДФЛ транспортный файл РНУ НДФЛ (ПНФ) может потребоваться удалить. ФП НДФЛ предоставляет метод удаления ПНФ по её номеру. Процесс строится **по аналогии с отправкой**: ручка переводит файл в промежуточный статус, задание подхватывает записи в этом статусе и выполняет запрос в ФП НДФЛ через шлюз **SOWA**.

Результат каждой операции (успешной и неуспешной) фиксируется в журнале `rnu_report.rnu_xml_sending_log`; актуальное состояние файла отражается в `rnu_report.xml_file.state`.

---

## Изменение модели данных

### Расширение enum `xml_file.state`

К действующим значениям (`CREATED`, `SEND_PROCESSING`, `SEND_SUCCESS`, `SEND_ERROR`) добавляются:

| Значение | Описание |
|---|---|
| `DELETE_PROCESSING` | Файл в процессе удаления из ФП НДФЛ |
| `DELETE_SUCCESS` | ПНФ успешно удалена из ФП НДФЛ |
| `DELETE_ERROR` | Ошибка удаления ПНФ |

### Журнал `rnu_xml_sending_log`

Доработка enum **не требуется** — действующие значения покрывают операцию удаления:

| Поле | Значение для операции удаления |
|---|---|
| `operation_code` | `UPLOAD` |
| `operation_type` | `DELETE` |
| `operation_status` | `SUCCESS` / `ERROR` |

В рамках одного `xml_file_id` в журнале может быть **несколько записей** (создание, отправка, повторная отправка, удаление) — это штатное поведение. Актуальное состояние файла хранится в `xml_file.state`.

# БЛОК 1. Перевод файлов на шаг «В процессе удаления»

## Шаг 1. Триггер

Выполняется запрос `POST /v1/report/rnu/xml/pnf/delete`, который в теле содержит следующие параметры:

| Поле | Тип | Описание | Обяз. |
|---|---|---|---|
| `jobId` | string (uuid) | Идентификатор задания | Да |
| `xmlFileId` | array (string, uuid) | Идентификаторы XML-файлов | Нет |

## Шаг 2

Поиск значения атрибута `jobId` в поле `id` таблицы `rnu_report.job`.
- **а.** Найдено → следующий шаг.
- **б.** Не найдено → АС п.1. Завершить сценарий.

## Шаг 3

В таблице `rnu_report.job_period` найти `id`, где `job_id` = `jobId` из запроса. Зафиксировать значения.

## Шаг 4

В таблице `rnu_report.xml_file` отфильтровать записи по `job_period_id` из шага 3.
- **а.** Не найдено → АС п.2. Завершить сценарий.
- **б.** Найдено → зафиксировать `xml_file.id`, перейти на следующий шаг.

## Шаг 5

Вводится переменная **N** — общее количество XML-файлов, участвующих в проверке. Процесс завершается, когда все дошедшие до шага записи ошибочные:
- если количество ошибочных = **N** → HTTP 400 с общим текстом ошибки;
- если количество ошибочных < **N** → HTTP 200 с детализацией по каждому элементу.

## Шаг 6

Проверить, заполнен ли атрибут `xmlFileId` в запросе.
- **а.** Не заполнен → зафиксировать значения из шага 4 и их количество, присвоить **N**.
- **б.** Заполнен → количество элементов `xmlFileId` присвоить **N**, найти их среди значений шага 4:
  - ни одного не найдено → АС п.3. Завершить сценарий;
  - есть найденные → по ним продолжить сценарий; по ненайденным зафиксировать ошибку АС п.4, `"status" = "error"`.

## Шаг 7. Проверка статуса файла

Для каждого элемента проверить: `xml_file.state` = **`SEND_SUCCESS`** или **`DELETE_ERROR`**.

- **а.** Проверка не пройдена по всем элементам и количество ошибочных = **N** → АС п.5. Завершить сценарий.
- **б.** Проверка не пройдена по части элементов → для них зафиксировать ошибку АС п.6, заполнив `<*>` значением `xml_file.state`, `"status" = "error"`.
- **в.** Есть элементы, прошедшие проверку → продолжить сценарий.

> **Обоснование перечня статусов.** Удаление применимо только к файлу, который фактически создан в ФП НДФЛ, то есть у которого заполнен `ndfl_form_id` — это состояние `SEND_SUCCESS`. Значение `DELETE_ERROR` включено для возможности повторной попытки удаления. Перечень **разрешительный**: любое иное значение `state` (включая `CREATED`, `SEND_PROCESSING`, `SEND_ERROR`, `DELETE_PROCESSING`, `DELETE_SUCCESS`) блокирует операцию.

## Шаг 8

Дополнительно проверить, что у элемента заполнено поле `ndfl_form_id`.
- Не заполнено → зафиксировать ошибку АС п.7, `"status" = "error"`.
- Заполнено → продолжить сценарий.

## Шаг 9

Посчитать количество элементов, прошедших проверки. Для записей `rnu_report.xml_file` с `id`, равным идентификатору элемента, заполнить/изменить поля:

| Поле в БД | Алгоритм формирования |
|---|---|
| `state` | Устанавливается значение `DELETE_PROCESSING` |
| `updated_at` | Установить текущую дату и время |

> Поле `xml_file.request_id` **не изменяется** — в нём сохраняется идентификатор запроса на отправку. Идентификатор запроса на удаление (`Request-Id`) генерируется отдельно в БЛОКЕ 2 и фиксируется только в журнале `rnu_xml_sending_log`. Это исключает потерю id отправки; связь операции удаления с ответом ФП восстанавливается через журнал.

## Шаг 10

Завершить сценарий, вернув HTTP 200 и заполнив в теле ответа:

| Поле | Тип | Алгоритм заполнения |
|---|---|---|
| `xmlFileTotal` | integer | Равно значению переменной **N** |
| `xmlFileSuccess` | integer | Равно количеству элементов, рассчитанных на шаге 9 |
| `details` | array | Заполняется для каждого идентификатора файла (`xmlFileId`) |
| `details.xmlFileId` | string | Идентификатор файла |
| `details.status` | enum | `success` — для элементов с шага 9; `error` — для элементов с ошибкой |
| `details.errorCode` | string | Для элементов с ошибкой — код согласно АС |
| `details.errorMessage` | string | Для элементов с ошибкой — описание согласно АС |

# БЛОК 2. Удаление ПНФ в ФП НДФЛ

## Запрос

**Триггер запуска.** Как только в таблице `rnu_report.xml_file` появляются записи со значением поля `state` = `DELETE_PROCESSING`, необходимо выполнить удаление ПНФ в ФП НДФЛ.

Используется метод ФП НДФЛ **`DELETE /ndfl_form/{ndflFormId}`** (спека «Метод удаления ПНФ», тип запроса — **синхронный**).
**Примечание:** для передачи данных между Пульс и ФП НДФЛ используется шлюз **SOWA**. **Один файл — один запрос.**

### Атрибуты запроса (path)

| Поле | Тип | Описание | Алгоритм заполнения |
|---|---|---|---|
| `ndflFormId` | string | Идентификатор (номер) ПНФ, которую необходимо удалить. `pattern: ^\d{1,19}$`, maxLength 19 | Заполняется значением поля `xml_file.ndfl_form_id` |

### Атрибуты запроса (headers)

| Поле | Тип | Описание | Алгоритм заполнения |
|---|---|---|---|
| `Request-Id` | string | Идентификатор запроса. `format: uuid`, maxLength 36 | Генерируется новый uuid на операцию удаления. Фиксируется в журнале `rnu_xml_sending_log.request_id`; поле `xml_file.request_id` не перезаписывается |
| `ASNU-Code` | string | Код системы-источника. `pattern: ^\d{4}$`, maxLength 4 | Заполняется значением `rnu_setting.constant_set.value` при условии `parameter = asnu_code_pulse` |

## Успешный ответ

В случае успешного удаления ПНФ система возвращает **HTTP-Status = 200**. Тело ответа — `application/json`:

| Поле | Тип | Описание |
|---|---|---|
| `rqId` | string (uuid) | ID запроса, полученный от АСНУ |
| `ndflFormId` | string | Идентификатор (номер) удалённой ПНФ |
| `deletionDateTime` | string | Дата и время удаления ПНФ (ISO8601) |

**Пример:**
```json
{
  "rqId": "f4be820d-0c4e-6754-807d-9f63aac7f27d",
  "ndflFormId": "45927",
  "deletionDateTime": "2023-05-17T12:00:00.000Z"
}
```

При получении успешного ответа найти запись файла в таблице `xml_file` и заполнить:

| Поле в БД | Алгоритм формирования |
|---|---|
| `state` | Установить значение `DELETE_SUCCESS` |
| `updated_at` | Установить текущую дату и время |

> `ndfl_form_id`, `ndfl_form_status`, `ndfl_form_URL` **не очищаются** — сохраняются для истории (номер удалённой формы нужен для разбора и повторных обращений). `ndfl_form_status` намеренно не сбрасывается: `state = DELETE_SUCCESS` уже однозначно указывает, что формы нет, рассогласования для читающего не возникает.
>
> `deletionDateTime` (дата и время удаления) **генерируется на стороне ФП НДФЛ** и приходит в ответе — вычислять её не требуется. В таблице `rnu_xml_sending_log` отдельного поля под неё нет; факт и время операции фиксируются в `created_at` записи журнала. Добавление отдельного поля под `deletionDateTime` в текущей версии не предусмотрено.

Зафиксировать запись в журнале `rnu_report.rnu_xml_sending_log`:

| Поле в БД | Алгоритм формирования |
|---|---|
| `operation_code` | `UPLOAD` |
| `operation_type` | `DELETE` |
| `operation_status` | `SUCCESS` |
| `xml_file_id` | Идентификатор записи `xml_file` |
| `request_id` | Заполняется значением атрибута `rqId` из ответа |
| `ndfl_form_id` | Заполняется значением атрибута `ndflFormId` из ответа |
| `created_at` | Установить текущую дату и время |

Поля `ndfl_form_status`, `ndfl_form_URL`, `error_code`, `error_type`, `error_name`, `error_message` не заполняются.

Обновить запись в таблице `xml_file`:

| Поле в БД | Алгоритм формирования |
|---|---|
| `state` | Установить значение `DELETE_ERROR` |
| `updated_at` | Установить текущую дату и время |

Зафиксировать запись в журнале `rnu_report.rnu_xml_sending_log`:

| Поле в БД | Алгоритм формирования |
|---|---|
| `operation_code` | `UPLOAD` |
| `operation_type` | `DELETE` |
| `operation_status` | `ERROR` |
| `xml_file_id` | Идентификатор записи `xml_file` |
| `request_id` | Заполняется значением атрибута `rqId` из ответа |
| `error_code` | Заполняется значением атрибута `errorCode` из ответа |

## Обработка зависших в `DELETE_PROCESSING` (таймаут)

Запрос в ФП НДФЛ синхронный, но ответ может не прийти (таймаут, обрыв соединения, недоступность SOWA). В этом случае файл остаётся в статусе `DELETE_PROCESSING` и не подхватывается повторно — этот статус не входит в перечень, доступный к удалению (шаг 7 БЛОКА 1). У ФП НДФЛ механизма таймаута нет, поэтому обработка зависших — на стороне ReportsTax.

**Правило:** если запись `xml_file` находится в статусе `DELETE_PROCESSING` дольше порогового времени `T_delete_timeout` (значение задаётся константой в `rnu_setting.constant_set`, ориентировочно 30 минут — согласовать) и ответ от ФП НДФЛ не получен, фоновая проверка:
- переводит `xml_file.state` = `DELETE_ERROR`, `updated_at` = now;
- фиксирует в журнале `rnu_xml_sending_log`: `operation_status` = `ERROR`, `error_message` = «Превышено время ожидания ответа ФП НДФЛ при удалении ПНФ».

После перевода в `DELETE_ERROR` файл снова доступен к удалению и будет подхвачен при следующем запуске ручки — отдельная процедура разбора не требуется.

> **Важно (самовосстановление при ложном таймауте).** Удаление у ФП НДФЛ отложенное, поэтому возможна ситуация: ФП удаление выполнил, но ответ до нас не дошёл. При повторной попытке ФП вернёт код **1005** («Форма была удалена ранее»), который по правилу выше трактуется как `DELETE_SUCCESS`. Таким образом ложный таймаут корректно разрешается автоматически через повторный вызов.

Согласно Справочнику ошибок (pageId 23244344511), для метода `delete` возвращаются:

| errorCode | errorType | errorName | HTTP |
|---|---|---|---|
| 1004 | BUSINESS | Форма не найдена | 404 |
| 1005 | BUSINESS | Форма была удалена ранее | 410 |
| 1006 | BUSINESS | Нельзя удалить или обновить ТФ ПНФ, данные которой изменены или использованы для формирования КНФ | 423 |
| 1008 | BUSINESS | Нельзя удалить или обновить ПНФ в закрытом периоде | 423 |
| 9901 | TECHNOLOGICAL | Недостаточно прав | 403 |
| 9902 | TECHNOLOGICAL | Ошибка сохранения/удаления записи в БД | 500 |
| 9903 | VALIDATION | Отсутствуют обязательные параметры запроса | 400 |
| 9904 | TECHNOLOGICAL | Ошибки алгоритма обработки | 409 |
| 9905 | TECHNOLOGICAL | АСНУ не совпадает (`ПНФ.АСНУ ≠ ASNU-Code`) | 403 |

Структура кода: первые две цифры — «сущность» (1000 — форма, 1100 — ТФ, 2000 — справочники, 9900 — системные, технические и ошибки валидации), последние две — порядковый номер.

> Код **9905** взят из альтернативных сценариев «Алгоритма удаления ПНФ» (pageId 21597241651, шаг 5.a) — в общем Справочнике ошибок он отсутствует.

### Обработка ошибок

**Общее правило:** любая ошибка → `state` = `DELETE_ERROR`, запись в журнал с `operation_status` = `ERROR`.

**Исключение — код 1005 «Форма была удалена ранее» (HTTP 410):** трактуется как успех. Целевое состояние достигнуто — ПНФ в ФП НДФЛ отсутствует (форма находится в состоянии «Удалена»). В этом случае:
- `xml_file.state` = **`DELETE_SUCCESS`**, `updated_at` = now;
- в журнал `rnu_xml_sending_log` запись пишется **как есть — `operation_status` = `ERROR`, `error_code` = 1005** и остальные атрибуты ошибки из ответа.

Такое разведение фиксирует корректное актуальное состояние файла (форма удалена) в `state`, но сохраняет в истории факт, что удаление выполнил не данный вызов, а форма уже была удалена ранее.

## Взаимодействие с шлюзом SOWA

Отправка в ФП НДФЛ выполняется через SOWA, который дополнительно валидирует запросы на соответствие структуре, зарегистрированной на его стороне.

Действующий CR на SOWA по отправке: **HRPY-16824** «DevOps. Пульс — Новый сервис SOWA SA_RTX».

**Требуется:** согласовать с **Бочкарёвым А.** расширение пула запросов к SOWA новым методом (`DELETE /ndfl_form/{ndflFormId}`) — определить, достаточно ли действующего CR или требуется новый, и что необходимо передать со стороны ReportsTax (в т.ч. схемы для валидации). Сертификаты и настройки взаимодействия уже прописаны — принципиальных препятствий не ожидается.

По вопросам формата на стороне ФП НДФЛ контактное лицо — **Свершникова Елена**.

## Принятые решения (закрыты аналитиком)

- **Код 1005 → `DELETE_SUCCESS`** (в журнал — `operation_status = ERROR`, код 1005). Обоснование и алгоритм — в разделе «Обработка ошибок».
- **Зависший `DELETE_PROCESSING` → таймаут переводит в `DELETE_ERROR`** для повторной попытки. См. раздел «Обработка зависших».
- **`deletionDateTime`** генерируется ФП, отдельное поле не заводится — см. «Успешный ответ».
- **`xml_file.request_id` не перезаписывается**, `Request-Id` операции удаления — только в журнал. См. шаг 9 и БЛОК 2.
- **`ndfl_form_status`** после удаления не чистится. См. «Успешный ответ».

## Требует подтверждения (внешние стороны)

## ⚠ Стыковка: `DELETE_SUCCESS` нужно добавить в ТРИ ручки

После удаления ПНФ из ФП НДФЛ файл получает `state = DELETE_SUCCESS`. По действующим спецификациям с ним больше нельзя выполнить ни одной операции — все три ручки пускают только `{CREATED, SEND_ERROR}`. Чтобы файл/отчёт не оказался заблокированным навсегда, `DELETE_SUCCESS` требуется добавить в разрешённые статусы:

| № | Ручка | Зачем | Приоритет |
|---|---|---|---|
| 1 | Удаление отчёта — `DELETE /v1/rnu/report` (HRPY-24879) | Иначе ранее отправленный отчёт неудаляем навсегда | Обязательно |
| 2 | Удаление XML — `DELETE /v1/rnu/xml/{xmlFileId}` (pageId 21819558938) | Чтобы снести локальную XML-запись и пересоздать отчёт | Обязательно |
| 3 | Отправка — `POST /v1/report/rnu/xml/pnf/create` (pageId 22422324714) | Только если решим разрешать повторную отправку того же файла | Опционально |

**Повторная отправка того же файла** (вариант 3) — не рекомендуется: у ФП форма остаётся в состоянии «Удалена» (12), повторная отправка приведёт к конфликту. Штатный путь пересоздания отчёта — через удаление XML-записи (вариант 2) с последующим формированием нового XML.

Все три спецификации в зоне ReportsTax — решение принимается на нашей стороне.
