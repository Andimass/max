# Спецификация: переход `system_client_id` со СНИЛС на do_id при отправке НОБ Пульс в МС

**Задача:** ReportsTax · Task · Minor · Security Level K-3 · эпик «Q2.2026_Tax_Общие компоненты» · команда «Регуляторная отчётность (PY)» · 1 SP
**КЭ:** ReportsTax(8449473)
**Страница для размещения:** «02. Отправка НОБ (NOB2)», pageId 18246765391, раздел 2.2 «Интеграция с Мастер Системой» (топики 2.2.1 отправки и 2.2.2 ответа).
**Смежная задача:** `[HRPY-23866] SA. do_id…` (свериться на пересечения).

---

## 1. Контекст и обоснование

При отправке НОБ Пульс в Мастер Систему (МС НДФЛ) в параметр `system_client_id` в роли идентификатора клиента сейчас подставляется **СНИЛС**. По требованию бизнеса для сверки необходимо перейти на идентификатор 3 уровня — **do_id** (идентификатор договорных отношений, ДО).

Дополнительное обоснование (не только бизнес-требование): на текущий момент отправка частично **нерабочая** — сообщения уходят в **DLQ** (`MSNDFL.OPERATIONS_PULS-DLQ.V1`). Причина: `system_client_id` передаётся числом (number). Ранее (март) числовые значения проходили валидацию SEDR, но после обновления схем со стороны МС строгая валидация перестала пропускать number в этом поле. Перевод поля в строку (do_id — это UUID, т.е. строка) одновременно:
- выполняет бизнес-требование (идентификатор 3 уровня для сверки);
- устраняет причину падения сообщений в DLQ.

---

## 2. AS-IS (как сейчас)

Алгоритм формирования сообщения отправки (раздел 2.2.1), шаги:
1. **JOIN с `epk_person_relation.snils`** для получения СНИЛС.
2. Фильтрация по статусу.
3. Группировка по `epk_id`.
4. В разрезе `epk_id` — группировка по `operation_id`.
5. Раскладка по объектам `rate / base / tax`.

В теле сообщения, внутри `operations[] → epk_operations[]`, поле `system_client_id` = СНИЛС (пример значения `"652326"`).

JSON-схема отправки: `system_client_id` имеет тип **number** (minimum 0, maximum — 19 девяток). UUID в это поле не помещается и не проходит валидацию SEDR.

---

## 3. TO-BE (как должно быть)

### 3.1. Источник значения
В поле `system_client_id` подставляется **do_id**.
Источник — `employee_py_nob.do_id` (значение уже присутствует в строке, отправляемой в МС; заполняется из `resultSet.do_id` на этапе получения данных прогонов). Дополнительный JOIN не требуется.

**Шаг 1 алгоритма формирования сообщения (JOIN с `epk_person_relation.snils` ради СНИЛС) — удаляется.** Остальные шаги (фильтр по статусу, группировка по epk_id, по operation_id, раскладка rate/base/tax) — без изменений.

### 3.2. Группировка — без изменений
Группировка операций остаётся **по epk_id**. Структура массива `epk_operations` не разворачивается по do_id. МС рассчитывает НОБ в разрезе epk и не использует `system_client_id` для расчёта — значение этого поля для МС непринципиально. Меняется только содержимое поля (СНИЛС → do_id), структура сообщения сохраняется.

### 3.3. Тип поля и JSON-схемы
`system_client_id`: тип **number → string**.
Доработать **обе** схемы:
- схема **запроса** (топик отправки `SRC.MSNDFL.OPERATIONS_PULS.V1`, раздел 2.2.1);
- схема **ответа** (топик ответов `DST.MSNDFL.OPERATIONS_TO_PULS.V1`, раздел 2.2.2).

Длину поля (`maxLength`) задавать **с запасом** — на стороне SEDR строгая валидация, любое несоответствие → DLQ. UUID — 36 символов; рекомендуется заложить запас (например, `maxLength` существенно больше 36, по аналогии с тем, как в number стоял максимум в 19 девяток).

### 3.4. Валидация схем
Обновлённые JSON-схемы и примеры сообщений прогнать через валидатор **APIStudio SEDR**:
`https://apistudio-iamosh.sigma.sbrf.ru/#/tools/json` (сверху выбрать профиль **SEDR**).
В спецификацию приложить **валидные** примеры JSON (запрос и ответ) с do_id в `system_client_id`, прошедшие проверку.
