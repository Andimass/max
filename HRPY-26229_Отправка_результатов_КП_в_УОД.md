## 1. Что делаем

ReportsTax выполняет контрольные процедуры (КП) над РНУ НДФЛ — проверки 2001–2004. Когда прогон завершён и **все проверки пройдены**, в Kafka публикуется событие с результатом расчёта. УОД читает его и понимает, что расчёт можно пускать в сводно-расчётные и платёжные ведомости.

Случай с отклонениями в объём не входит — он покрывается отправкой в Payroll.Validator (HRPY-25913).

---

## 2. Триггер

`validation_run.status = DONE` **И** `validation_run.deviations_count = 0`.

При наличии отклонений событие не публикуется.

Отправка асинхронная: завершение прогона не должно блокироваться на время публикации.

---

## 3. Структура события

Строки группируются по паре (`kpp`, `oktmo`) — в рамках одного отчёта могут встречаться разные налоговые инспекции и территории. Сумма удержанного налога считается **внутри своей группы**, иначе платёжное поручение уйдёт не в ту инспекцию.

```json
{
  "header": {
    "calc_header_id": "uuid",
    "version": 1
  },
  "groups": [
    {
      "kpp": "770123456",
      "oktmo": "45000000000",
      "tax_hold": 1234.56,
      "calculation_lines": [
        { "person_id": "uuid", "do_id": "uuid", "date_for": "2026-01-01" }
      ]
    }
  ],
  "meta": {
    "kp_codes": ["2001", "2002", "2003", "2004"],
    "result": "PASS",
    "completed_at": "2026-08-11T10:00:00Z"
  }
}
```

Отдельного блока `report_meta` в структуре **нет** — `kpp`, `oktmo` и `tax_hold` живут на уровне группы.

### 3.1. Источники полей

| Поле | Источник | Примечание |
|---|---|---|
| `header.calc_header_id` | `calc_block.calc_header_id` | Через цепочку 4.1 |
| `header.version` | `calc_block.seqnr` | Версия расчёта от Организатора, собственной нумерации не заводим |
| `groups[].kpp` | `rnu_income.kpp` | varchar(9), ключ группировки |
| `groups[].oktmo` | `rnu_income.oktmo` | varchar(11), ключ группировки |
| `groups[].tax_hold` | `SUM(rnu_income.tax_hold)` **в пределах группы** | numeric(15,2). Именно удержанный налог, не `tax_calculated` |
| `…calculation_lines[].person_id` | `validation_result.person_id`, иначе резолв 4.2 | |
| `…calculation_lines[].do_id` | `rnu_income.do_id` | |
| `…calculation_lines[].date_for` | `rnu_income.income_date` | Дата начисления = период расчёта. Не `payment_date` (формируется позже, при ПВ) и не `tax_date` |
| `meta.kp_codes` | Коды активных проверок из реестра (`is_active = true`) | 2001, 2002, 2003, 2004 |
| `meta.result` | Константа `PASS` | Отправка только при отсутствии отклонений |
| `meta.completed_at` | `validation_run.finished_at` | Не `now()` |

⚠ Поля налога легко перепутать: `tax_calculated` — исчисленный, **`tax_hold`** — удержанный, `tax_not_hold` — исчисленный но не удержанный, `tax_over_hold` — излишне удержанный. Берём `tax_hold`.

## 4. Разрешение связей

### 4.1. Прогон → заголовок расчёта

Прямой связи между `validation_run` и `calc_block` в модели нет: `calc_block.run_id` — идентификатор прогона расчёта от УОД (событие второй подписи), а не наш `validation_run.id`.

Цепочка:

```
validation_run.job_id
  → job_period (job_id)
    → rnu_income (job_period_id) → do_id, kpp, oktmo, income_date, tax_hold
      → calc_block (do_id) → calc_header_id, seqnr
```

Правило выбора записи `calc_block`, если по одному `do_id` их несколько с разными `seqnr` — вынести в **конфигурируемую стратегию** (по умолчанию: последняя по `seqnr`), см. 11.2.

### 4.2. Резолв `person_id`

1. `validation_result.person_id`, если заполнен.
2. Иначе — `job_person` по паре (`job_id`, `do_id`): связка создаётся на этапе 2 формирования отчёта, эта же таблица используется при сборке отчёта для сопоставления доходов с персданными.

Не резолвится → строка отправляется без `person_id`, пишется WARN.

Вариант через `rnu_person_data` по `taxpayer_id` не используем: значение заполняется позже (этап 5) и при отсутствии ИНН/СНИЛС подменяется табельным номером.

## 5. Модель данных

```sql
CREATE TABLE rnu_audit.uod_sending_log (
    id                 UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    validation_run_id  UUID NOT NULL REFERENCES rnu_audit.validation_run(id),
    calc_header_id     UUID,
    version            INT,
    groups_count       INT,
    lines_count        INT,
    status             VARCHAR(20) NOT NULL DEFAULT 'NEW',  -- NEW / SENDING / SENT / FAILED
    attempt_count      INT NOT NULL DEFAULT 0,
    error_message      TEXT,
    payload            JSONB,
    sent_at            TIMESTAMP,
    created_at         TIMESTAMP NOT NULL DEFAULT now(),
    updated_at         TIMESTAMP NOT NULL DEFAULT now()
);

CREATE INDEX idx_usl_run    ON rnu_audit.uod_sending_log(validation_run_id);
CREATE INDEX idx_usl_status ON rnu_audit.uod_sending_log(status);
CREATE INDEX idx_usl_header ON rnu_audit.uod_sending_log(calc_header_id, version);
```

Kafka не даёт подтверждения обработки потребителем, поэтому журнал фиксирует факт публикации и результат callback'а продюсера. `payload` хранится для разбора инцидентов.

## 6. Алгоритм

```
1. Событие: validation_run.status → DONE
2. deviations_count > 0 → выход
3. По validation_run.job_id собрать строки rnu_income
   (через job_period), поля: do_id, kpp, oktmo, income_date, tax_hold
4. do_id → calc_block → calc_header_id, seqnr        (правило выбора — 11.2)
5. do_id → person_id (validation_result либо job_person)
6. Сгруппировать строки по (kpp, oktmo):
     для каждой группы — SUM(tax_hold) и массив calculation_lines
7. Собрать meta: kp_codes, result = PASS,
                 completed_at = validation_run.finished_at
8. INSERT uod_sending_log (status = NEW, payload)
9. Публикация в Kafka:
     успех  → status = SENT, sent_at = now()
     ошибка → status = FAILED, attempt_count + 1, отложенный повтор
```

### 6.1. Повторы и зависшие записи

- Повторы отложенные, через состояние в БД, а не удержанием потока.
- Предел попыток — 5, далее инцидент (по аналогии с отправкой НОБ в МС НДФЛ).
- Запись не должна остаться в `SENDING` навсегда: по таймауту переводится в `FAILED`. Та же дыра выявлена в HRPY-25121 (`DELETE_PROCESSING`).

### 6.2. Ограничение размера

Лимит на стороне УОД не подтверждён (11.1). Закладываем **конфигурируемый порог** `max-lines-per-message`: при превышении событие делится на несколько сообщений с сохранением целостности групп (группа не разрывается между сообщениями). До получения ответа порог держим заведомо большим и логируем фактические размеры — это даст статистику к разговору с УОД.

### 7.1. Конфигурация

```yaml
integrations:
  uod:
    enabled: ${UOD_INTEGRATION_ENABLED:false}
```

## 9. Критерии приёмки

| # | КОГДА | ТОГДА |
|---|---|---|
| 1 | Прогон завершён, отклонений нет | Событие опубликовано, `status = SENT`, payload сохранён в журнале |
| 2 | Прогон завершён, есть хотя бы одно отклонение | Событие не публикуется, запись в журнале не создаётся |
| 3 | В отчёте одна пара (КПП, ОКТМО) | В событии одна группа, `tax_hold` = сумма по всем строкам |
| 4 | В отчёте несколько пар (КПП, ОКТМО) | Групп столько же, у каждой своя сумма `tax_hold`; строки не смешиваются между группами |
| 5 | `person_id` не резолвится | Строка отправлена без него, WARN в лог |
| 6 | Число строк превышает `max-lines-per-message` | Событие разделено на несколько сообщений, ни одна группа не разорвана |
| 7 | Публикация не удалась | `status = FAILED`, `attempt_count + 1`, запланирован отложенный повтор |
| 8 | Исчерпан лимит попыток | Заведён инцидент, автоматические повторы прекращены |
| 9 | Ответ от Kafka не получен | Запись не остаётся в `SENDING`: по таймауту переводится в `FAILED` |
| 10 | `integrations.uod.enabled = false` | Событие не публикуется, ошибок не возникает |
| 11 | Квартальный отчёт крупного департамента | Завершение прогона не блокируется на время публикации |
